# Milestone 3 — Live synchronization: incremental sync, outbox, sending, and triage mirroring

> **Historical design and implementation record.** This document preserves the decisions made on its stated date and is not evidence of current behavior. [Leia o original em Português](2026-08-28-marco-3-sincronizacao-design.md).

Approved on 2026-08-28, together with the Milestone 2 specification
(`2026-08-28-marco-2-contas-design.md`), which is an integral prerequisite: this
milestone assumes the GRDB database as the source of truth, with `UNISync`,
`AccountDirector`, `GmailClient`, `ImapSession`, and initial loading ready.

Project-owner decisions that govern this work: **the cycle closes completely in this
milestone** — read, triage, AND send; **triage mirrors to the server**
(Today/Later follow you in every client); OAuth is Google only, everything else is IMAP.

## Objective

What happens on the server appears in the app within seconds; what you do in the app
happens on the server even if the network drops midway; and the composer actually sends.
At the end, OkamiUNI is usable as a single email client.

## Inherited constraints

The same ones as the Milestone 2 specification, verbatim — especially: the database is
the truth, the UI never waits for the network, errors are never swallowed, there are no
new dependencies beyond GRDB + swift-nio-imap, tests are proven by mutation, interactions
are proven by rehearsal in the real app, and **nothing limits provider/domain/number of
accounts**.

## The three new engines

### 1 · Incremental synchronization (server → database)

One **actor per account** (`AccountSyncWorker`), which owns its synchronization schedule:

- **Gmail**: `history.list` starting from the stored `historyId` — new and deleted
  messages, and label/flag changes become database writes. Trigger: when the window
  activates, after any of our operations, and polling every 60 seconds with the window
  active / every 5 minutes when unfocused. An expired `historyId` (404) → re-sync the
  initial load without deleting what the user did locally.
- **IMAP**: **IDLE** in the inbox (arrivals within seconds); other folders are scanned in
  the same trigger windows. Changed `UIDVALIDITY` → re-sync that folder from scratch.
  Use `CONDSTORE`/`HIGHESTMODSEQ` when the server provides them; otherwise compare flags
  by UID batch.
- Reconnection with exponential backoff + jitter; returning network (`NWPathMonitor`)
  wakes every worker.
- **Conflict**: the server wins for message state (flags, folder), except when one of our
  operations is still queued for that message — the queue reapplies it and the local state
  prevails until it empties (last-writer-wins with our pending write last).

### 2 · Outbox (database → server)

`outbox` table (created in database v2): typed operation, account, target,
payload, attempts, next retry instant, state
(`pendente`, `executando`, `falhou`, `feita`).

- Operations: `setRead`, `setFlagged`, `move(bucket)`, `delete`,
  `deletePermanently`, `emptyTrash`, `send`, `appendSent`,
  `createDepoisFolder`; `addToAgenda`/`removeFromAgenda` remain local (they have no
  server until Milestone 4).
- Every UI action writes the projection to the database **in the same transaction** that
  queues the operation — optimistic, atomic, and Milestone 1 Undo queues the inverse
  operation.
- An executor per account consumes in order, **coalescing** (read+unread+read on the same
  message becomes one operation; N `setRead` operations in the same folder become one
  batched IMAP `STORE` / Gmail `batchModify`).
- Idempotency: each operation carries a key; rerunning after an ambiguous timeout does not
  duplicate the effect (Gmail: `batchModify` is naturally idempotent; sending: see below).
- A permanent failure (a 4xx that retry cannot cure) stops that account’s queue, marks the
  account with the error, and the UI shows what and why, with "tentar de novo" and
  "descartar operação" — never a silent discard.

### 3 · Sending

- Composer/"Enviar" band → `outbox.send` with the assembled message (MIME for
  IMAP/SMTP; RFC 822 raw for the Gmail API `messages.send`).
- **Sending idempotency** (the only case where duplication is unacceptable): every send
  gets a `Message-ID` generated by us BEFORE the first attempt; after a timeout, retry
  first searches Sent for that `Message-ID` — if found, it counts as sent.
- **SMTP**: our own submission client over SwiftNIO (the submission protocol is small:
  EHLO, STARTTLS/implicit TLS, AUTH PLAIN/LOGIN, MAIL/RCPT/DATA), with host/port presets
  by provider alongside IMAP presets. After 250, `APPEND` a copy into Sent (except for
  providers that save it themselves — the preset says so).
- **Gmail**: `messages.send`; Gmail saves to Sent itself.
- Visible state: "Enviando…" on the message, failure with its cause and "Tentar de novo"
  — the Milestone 1 receipt language.
- The **Sent** mailbox enters the sidebar (role `sent`), outside triage.
- Composer rich text → MIME `multipart/alternative` (plain text + HTML generated from
  `NSAttributedString`); seed attachments become MIME parts.

## Triage mirroring

| Bucket | Gmail | IMAP |
|---|---|---|
| Today | in INBOX, without the `OkamiUNI/Depois` label | in INBOX |
| Later | **`OkamiUNI/Depois`** label (created on first use; INBOX leaves with it so webmail does not duplicate it) | **`OkamiUNI/Depois`** folder (created on first use) |
| Archived | remove INBOX (All Mail) | Archive folder (role `archive`) |
| Trash | TRASH label | Trash folder |
| Flagged | STARRED | `\Flagged` |
| Read | remove UNREAD | `\Seen` |

- The reverse projection (server → bucket) is the same pure function from Milestone 2,
  extended — change there, change here, **one place only**.
- Moving to Later in another client (dragging to the folder in webmail) appears here as
  Later: mirroring is bidirectional for free because incremental reading already projects it.
- "Esvaziar lixeira" → batch Gmail `messages.delete` (permanent); IMAP `STORE \Deleted`
  + `EXPUNGE` in Trash. It remains behind the Milestone 1 confirmation.

## Database changes (v2 migration)

`outbox`; `folder` gains `depois` as a materialized role; `message` gains
`pendingOps` (a denormalized count for the conflict above); indexes support executor
queries. Nothing destructive — v1 → v2 preserves everything.

## What changes in existing packages

- `UNIShell`: Sent mailbox in the sidebar; "Enviando…"/failure states; pending-queue
  badge on the account row (n operations waiting for the network). The rest of the shell
  **does not change** — Milestone 1 actions already call `MailStore`, which now queues.
- `UNICore`: `MailStore` delegates mutations to UNISync’s write port (`MailCommandPort`
  protocol); in fixture mode, the port is in memory and current behavior remains intact
  (all Milestone 1 tests continue to apply unchanged).

## Errors and observability

The Milestone 2 `SyncError` covers errors; account queue state is added. The Accounts
window panel shows last synchronization, pending operations, and the last failure with its
cause. Structured logs are per account/component.

## Tests

- Queue executor: ordering, coalescing, backoff retry, idempotency
  (ambiguous timeout → no double effect), permanent failure stopping the queue — all
  against fake ports, with no network.
- Conflict: local-pending × server-change matrix, boundary by boundary.
- SMTP: against a fake NIO server (EHLO/AUTH/DATA scripts, including a drop midway through
  DATA and an ambiguous post-DATA response).
- Incremental Gmail: recorded `history.list`, including expired-history 404.
- IMAP: IDLE wakeup, UIDVALIDITY changing midway, CONDSTORE present and absent.
- MIME: round-trip generation and reading (text+HTML+attachment), with accents and
  quoted-printable.
- Mirroring: bucket → operations → fake-server state → reread → same bucket (the cycle
  closes).
- Real-app rehearsal: send from composer through local fake SMTP and see the state move;
  archive offline and see the queue empty when the “server” returns.

## Out of scope (recorded)

Microsoft Graph; real Gmail push (Pub/Sub — polling + IDLE are sufficient for now);
threads/conversations; delayed undo-send; server calendar (Milestone 4, EventKit);
rules/filters; multiple identities per account.

## Milestone acceptance criterion

With the same two accounts from Milestone 2: a new email arrives automatically within
seconds; archive/delete/flag/Later are reflected in webmail (and Later done in webmail is
reflected here); sending from the composer reaches the recipient with a copy in Sent;
dropping the network in the middle of all this loses no action — the queue empties when
the network returns, with visible state throughout.
